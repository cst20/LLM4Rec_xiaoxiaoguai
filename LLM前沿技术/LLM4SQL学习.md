
# How to Get Your Agent Near 100% Accurate Data

2026年4月11日的博客
本文学习google的博客，主要理解为什么LLM写SQL不可靠，以及google QueryData的解决思路，是对Schema的列名做一个解释，以及对于prompt中的一些经常出现的关键业务问题，提前为关键业务问题提供标准化并且可控的 SQL 生成规则。
总而言之，我觉得思路很简单，就是通用能力是来自于LLM本身，然后为写SQL的agent提供类似于SKILL的东西（比如schema的解释或者关键业务问题的模版）

## 为什么 LLM 写 SQL 仍然不够可靠？

LLM 非常擅长写查询代码。给它一段数据库 schema，它通常能生成看起来很合理的 SQL。但问题在于，**为一个真实数据库写出准确查询，需要的不只是 SQL 能力，也不只是解析数据库模式。**
真实业务数据库里有很多隐含信息，schema 本身往往无法完整表达。

### 1. Schema 可能并不清晰

开发人员经常使用缩写、简称，甚至只有业务内部才懂的命名方式。
比如一列叫 `product`，它到底表示什么？
它可能是产品类别，也可能是具体型号，也可能是业务线。如果列名变成 `prod`，甚至只是 `p`，歧义会更严重。
LLM 看到这些字段名时，只能根据通用语义猜测。但业务数据库里的命名并不总是符合通用语义。

### 2. 字段值可能存在歧义

即使列名看起来明确，字段值也可能让人困惑。比如有一列叫“订单退货状态”，里面的值是整数：`1`、`2`、`3`。哪个代表“已退货”？哪个代表“退货中”？哪个代表“已发起退货申请”？

如果没有额外上下文，LLM 很容易生成错误的过滤条件。

### 3. Schema 不包含业务逻辑

数据库 schema 描述的是数据结构，但业务问题需要的是业务语义。

例如，业务上可能把“月活跃用户”定义为：

> 当月至少发布过一次内容的用户。

而不是简单地定义为：

> 当月登录过的用户。

这类定义通常不会直接出现在数据库字段名里。如果只靠 schema，LLM 很难知道应该使用哪张表、哪个事件、什么过滤条件。

### 4. 自然语言问题本身可能不明确

用户的问题也经常带有歧义。比如：“最新促销是什么？”这里的“最新”指创建时间最新？上线时间最新？还是最近仍然有效的促销？如果 Agent 不识别这种歧义，而是直接生成 SQL，就很容易给出一个看起来合理但实际上错误的答案。

## QueryData 的思路：给 LLM 补上数据库上下文

QueryData 的核心思路是：利用 Gemini LLM，再结合描述业务数据库的上下文，让 Agent 不只是“会写 SQL”，而是更懂这个数据库。

这里的数据库上下文，本质上就是驱动 QueryData 的一组描述和指令，主要包括两类：

1. **模式本体（Schema Ontology）**
2. **查询意图（Query Blueprint）**

此外，作为最后一道防线，当 QueryData 判断问题无法被可靠回答时，它会提出澄清问题，而不是强行生成一个可能错误的查询。

## 一、模式本体：让 Agent 理解数据的真实含义

模式本体的目标，是帮助 LLM 理解数据库结构背后的语义。它不只是告诉 Agent 有哪些表、哪些列，更重要的是告诉它：

* 这张表代表什么业务对象？
* 这一列的真实含义是什么？
* 字段值分别代表什么状态？
* 哪些表和列更适合回答某类问题？

可以把模式本体理解为一组给 LLM 的“线索”或“提示”。它帮助 LLM 在面对自然语言问题时，选择正确的表、正确的字段，并把它们组合成正确的数据库查询。

比如，对于一个房地产搜索引擎，可以有这样的数据库级描述：

> Listings, real estate agents and information about communities where listings are located – schools, amenities and hazards: fire, flood and noise.

对于 `property` 表，可以有这样的表描述：

> Current real estate listing, including houses, townhomes, condos and land.

对于 `proximity_miles` 这一列，可以有这样的列描述：

> property distance from the district’s school in miles.

这些描述虽然看起来简单，但对 LLM 非常关键。因为没有这些上下文时，LLM 只能根据字段名猜测；有了这些本体描述后，它更可能理解字段的业务含义。

为了降低维护成本，这些描述也可以自动生成。比如可以根据字段名、表关系、示例值，为每个表和列生成更丰富的自然语言解释。

## 二、查询蓝意图图：对关键业务问题进行精确控制

如果说模式本体是“词汇表”，那么查询意图就是“标准解题步骤”。模式本体帮助 Agent 理解字段含义，而查询意图则进一步规定：面对某些重要业务问题时，应该如何生成 SQL。
为什么需要查询意图？因为很多业务问题不是简单地选择一张表、过滤几个字段就能解决的。它们背后往往有业务定义、排序逻辑、阈值设定，甚至是经过 A/B 测试验证过的经验公式。

例如，用户问：

> 靠近优质学校的河畔住宅。

Gemini 可能会生成类似这样的逻辑：

```sql
WHERE city_name = 'Riverside'
  AND school_ranking <= 5
ORDER BY proximity_miles ASC
```

这个结果看起来不错，但仍然不够严谨。因为“靠近优质学校”并不是一个简单条件。学校排名和房屋到学校的距离，都应该影响最终排序。如果某所学校排名特别好，用户可能愿意多开一英里；如果学校一般，即使距离近，也未必是最优选择。因此，一个严谨的系统不应该把这种业务判断完全交给 LLM 临场发挥，而应该通过查询意图进行控制。

## 模板：把自然语言意图映射到参数化 SQL

查询意图的一个核心形式是模板。模板可以理解为：

> 一组自然语言意图，以及与之对应的参数化 SQL。

例如：
```text
parameterized_intent:
"$1 houses close to good schools"

parameterized_SQL:
SELECT …
FROM …
WHERE city_name = $1
  AND school_ranking <= 5
  AND proximity_miles <= 2
ORDER BY school_score(school_ranking, proximity_miles)
```

这里的关键不只是 SQL 模板本身，而是 `school_score` 这个排序函数。它把学校排名和距离综合成一个分数，而不是让 LLM 自己临时决定什么叫“靠近”、什么叫“优质”。

这种方式有两个好处。第一，关键业务问题的答案会更加准确、稳定。第二，Agent 可以解释它是如何理解用户问题的。例如它可以告诉用户：“我将‘靠近优质学校’解释为学校排名小于等于 5，距离小于等于 2 英里，并使用综合分数排序。”

这种可解释性非常重要。即使偶尔出现误差，人工干预者或者上层 Agent 也能理解 QueryData 的答案到底意味着什么。

## Facets：让模板既准确又灵活

普通模板的问题是灵活性有限。

它们只能回答预先设计好的关键问题模式。

比如你可以设计一个模板回答：

> 靠近优质学校的住宅。

但用户可能会继续组合更多条件：

> 靠近优质学校、价格在 80 万到 120 万之间、至少 3 个卧室、面积超过 2000 平方英尺的住宅。

如果每一种组合都写一个完整模板，维护成本会非常高。

Facets 的作用，就是把模板中的条件模块化。

例如：

```json
{
  "parameterized_intent": "Property price between $1 and $2",
  "parameterized_sql_snippet": "T.\"price\" BETWEEN $1 AND $2"
}
```

这样，系统可以把多个 facet 组合起来，生成既符合业务逻辑、又能覆盖大量自然语言问题的 SQL。

也就是说，Facets 让 QueryData 同时获得两种能力：

1. 对关键业务逻辑保持高准确率；
2. 对用户自然语言问题保持足够灵活。

## 三、值搜索：解决数据库私有值带来的歧义

还有一类歧义，不在 schema 里，而藏在数据值本身。

这类问题需要 LLM 和数据库协作解决。

例如用户问：

> Westwood 在过去一个月内售出的房产数量。

这里可能有两个问题。

第一个问题是拼写错误。用户可能想说的是某个近似名称。

第二个问题是更深层的业务歧义：在数据库里，`Westwood` 可能既是一家房地产经纪公司的名称，也可能是一个城市的名称。

如果 Agent 直接把 `Westwood` 当成城市过滤，可能错；如果当成经纪公司过滤，也可能错。

这时就需要值搜索。

值搜索利用数据库中的文本搜索和向量搜索能力，把自然语言问题里提到的实体，与数据库里的真实值进行匹配。

它可以发现：

* `Westwood` 是否是某个城市名；
* `Westwood` 是否是某个经纪公司名；
* 是否存在拼写相近的值；
* 哪些候选值更可能对应用户意图。

如果仍然无法确定，QueryData 就不应该强行选择一个答案，而应该提出澄清问题：

> 你说的 Westwood 是指城市，还是房地产经纪公司？

这一步非常关键。

一个高质量数据 Agent 的目标不是永远回答，而是在不确定时知道自己不确定。

## 四、澄清问题：最后一道准确性防线

当自然语言问题本身有歧义，或者 schema、本体、模板、值搜索都无法提供足够确定的判断时，QueryData 会提出澄清问题。

这并不是失败，而是接近 100% 准确率所必须的机制。

很多数据错误的根源，不是模型不会写 SQL，而是模型在问题不明确时仍然强行回答。

一个可靠的数据 Agent 应该能区分两种情况：

1. 我知道该如何查询；
2. 我需要更多信息才能查询。

比如“最新促销”这种问题，如果系统不知道“最新”到底指创建时间、上线时间还是仍然有效的活动，就应该先澄清，而不是随便选一个时间字段。

## 总结：数据 Agent 的准确率来自上下文工程

QueryData 的核心启发是：

> 想让 Agent 在数据查询任务上接近 100% 准确，不能只依赖 LLM 的通用 SQL 能力，而要为它提供足够丰富、足够业务化的数据库上下文。

这个上下文主要包括：

1. **模式本体**：解释表、列、字段值的真实业务含义；
2. **查询意图**：为关键业务问题提供标准化、可解释、可控的 SQL 生成规则；
3. **模板与 Facets**：在准确性和灵活性之间取得平衡；
4. **值搜索**：解决自然语言实体与数据库私有值之间的匹配问题；
5. **澄清机制**：在不确定时提问，而不是强行回答。

LLM 本身已经非常擅长写 SQL，但真实业务数据库的难点不只是 SQL 语法，而是语义、业务逻辑和歧义消解。

所以，构建高准确率数据 Agent 的关键，不是简单地把 schema 塞进 prompt，而是系统性地构建一套围绕数据库的语义层和查询控制层。

换句话说：

**LLM 负责生成能力，数据库上下文负责准确性。**

只有把这两者结合起来，数据 Agent 才有可能从“看起来大多数时候是对的”，走向“在真实业务里足够可靠”。
